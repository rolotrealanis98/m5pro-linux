# Full-support gap map: MacBook Pro 16-inch M5 Pro (J716s, T6050) under Linux/Omarchy

Updated 2026-11-22 (UTC) on the Mac Studio (rows: boot, storage.sdxc, display brightness/HDR/HDMI, GPU, camera, ANE, deep sleep, USB host, update path, session, upstream); before that 2026-11-17; first written 2026-11-08. Sources for this update: the MacBook's live state
(read-only: kernel 7.3.0-gec5f49f167be, branch `j716s-touchid` = `j716s-next6b` + Touch ID, the everyday boot since
2026-11-17), the attended queue and runbooks in the work volume (`bench/requests/`), the repository's `contrib/pending/*`
and `contrib/omarchy-mac/` reports, and the open and merged pull requests of aurora-silicon/linux, mesa, aura and
aurora-sep-userspace (and omacom) since 2026-11-08. Nothing was changed on the MacBook. Machine-readable twin:
[`gap-map.csv`](gap-map.csv) (same rows, same columns; the tables below are generated from it). Status words used
everywhere: **works** (daily or test payload, with a result log), **partial** (works with a named hole), **prepared**
(patches/DT built, never booted or booted without the feature proven), **blocked** (tried, stopped by a hang or a missing
piece), **missing** (nothing written here yet), **in progress** (another agent is working on it right now; the row names the
request document that carries it and keeps the last verified state), **not planned**. (**in study**, used on 2026-11-08, is
retired: all four studies are written.) Effort uses the repo scale (S <= 2 days, M <= 2 weeks, L <= 2 months, XL = new
driver or protocol RE, no date). "Elsewhere" names who already has the feature: Asahi (M1/M2), Aurora (M3/M4/M5 family; the
sibling 16-inch machines J716c and K116s and the 14-inch J714s are now the closest precedents), or nobody.

No per-unit value appears in this file or in the CSV: only node names, compatible strings, property names, register
offsets and sizes. The ADT dump, the N1 firmware, calibration data and NVRAM contents stay off the repository.

## 1. One-screen summary

- **96 capabilities** across 18 domains: **25 work, 31 partial, 13 prepared (built, unproven), 6 in progress (other agents),
  16 missing, 5 not planned**, no blocked rows. On 2026-11-08 the same table counted 94 rows: 20 works, 27 partial, 12
  prepared, 2 blocked, 23 missing, 4 in study, 6 not planned (the CSV had drifted to 21/29/12/2/21/4/5 by the time this
  update started). Two rows are new (customization tracking, protected video). These counts are from 2026-11-17; the
  2026-11-22 row update moved camera.isp to works, display.hdr and desktop.update-path to partial, display.hdmi to prepared.
- **What moved since 2026-11-08** (each checked on the live machine or in a result log): Touch ID works end to end; the
  ambient light sensor works; x86-64 programs run through qemu binfmt and Docker; Omarchy's fq/BBR sysctls work; power
  profiles switch; screen-off-when-idle, the 80 % charge limit and the desktop defaults are applied; Wi-Fi joins open
  networks; the speaker protection (v2) is verified; aura stage 2 is the everyday loader; the root filesystem is checked
  at every boot. Built but not run: deep sleep, the DCP's display power-down, trackpad palm rejection, idle parking, the
  left-back port as a host. Upstream: the J716s DT, N1 training, the display method IDs, the GPU recovery fixes and native
  GL are merged; the 14-inch J714s and K116s siblings merged suspend-to-RAM, external displays, USB4, ALS, lid angle and
  video decode DTs, and the M5 Max J716c has a deep-sleep series open.
- **What a user has today**: 18 cores, NVMe root with a boot-time fsck, keyboard, backlight, trackpad with haptics,
  Touch ID (sudo, polkit, lock screen), ambient light sensor, battery with an 80 % limit, s2idle with the lid, both
  front Type-C ports as USB3 hosts, Wi-Fi (HE, 2.4/5 GHz, open networks) and the Bluetooth controller (nothing paired),
  speakers under protection and mics, the DCP driving the panel at 120 Hz with VRR and screen-off when idle, GPU
  acceleration (Vulkan, zink), Hyprland on Omarchy 4.5, KVM initialised, x86-64 containers, NVRAM read, an A/B boot
  chain with a watchdog.
- **The gaps that decide whether this is a laptop or a demo**: (1) sleep: s2idle only (4.3-4.4 W measured on battery) and no deep
  sleep or clock-alarm wake proven; (2) Thunderbolt/USB4 and with it docks and external displays (the daily DT leaves the
  routers off); (3) the speaker listening test is half done; (4) Bluetooth never paired; (5) the GPU InitData capture that
  unblocks the upstream driver; (6) packages and installer (linux-aurora 7.2.11 has no T6050; mesa-aurora has no G17; the
  Omarchy installer refuses M4+); (7) no deeper idle than WFI and no DRAM DVFS, so the power budget stays about 2x macOS.
- **What Asahi delivers on M1/M2 that the J716s still lacks** (their M5 page is all TBA, so every T6050 feature comes
  from Aurora and omacom): external displays and HDMI, camera, SD card slot, video decode in the daily, NVRAM write via
  `asahi-bless`, an installer, a measured sleep ladder. (The ambient light sensor is no longer on this list.)
- **What Aurora adds on M3/M4 that the J716s still lacks**: HDR/EDR output, Thunderbolt + DP tunnels on the daily, ANE
  driver, video encode and ProRes, deep sleep and RTC wake, NVRAM writes, speaker profiles upstream, `aura recover`.
  Touch ID, KVM and Aura stage 2 are no longer on this list.
- **What macOS does that no Linux on Apple Silicon has a name for yet** (from the macOS 27.3 kext list and the ADT):
  the always-on display coprocessor (`aod2`), voice trigger and always-listening mics, USB audio offload (`auss`),
  the AES engine, the USB-C retimers (`uatcrt0..2`), the DP input muxes (`atc*-dpin*`), the panel TCON and its PMIC/EEPROM/temperature
  sensors (owned by the DCP firmware), the BTM battery/thermal monitor, NFC, the exclave services (ISP, ANE, SEP
  manager, privacy indicator brightness), hibernation, secure boot with signed kernels.
- **Hardware inventory**: 608 classified ADT rows as of 2026-11-08 (section 4; not recounted, see the note there).

## 4. Hardware inventory: every ADT node under `/arm-io` and at the top level, classified

Status of this section: the classification below is the 2026-11-08 one and was not recounted (the ADT is private and was
not re-read for this update). Blocks that have moved class since, from the live kernel and the DT PRs: `sep` (driven: Touch ID),
`aop` ALS and lid-angle nodes (driven), `avd0`, `ave0`, `apr0`, `jpeg0/1` and their DARTs (now in the everyday DT; AVD waits for
one firmware file, ProRes for an init table), `sio` (module loaded), `acio*`/`apciec*` (still test DTs only; the everyday leaves
the routers off), the display crossbar (module loaded), `ane0` (firmware regions reserved, no node driven). Recount when the
next ADT walk happens.

Method: the runtime ADT of this unit was parsed node by node (626 inventory rows; 608 classified after folding 156
`iommu-mapper` nodes into `iommus=` and 23 RTKit `iop-nub` nodes into their coprocessor). Each node with a
`compatible` was matched against the daily kernel tree (`wt-daily-dcp`, branch `j716s-daily-dcp`: the compiled
`t6050-j716s.dts` has 267 nodes, 167 with a compatible), against every other `t6050-j716s*.dts` in the worktrees
(`wt-tb`, `wt-video`, `wt-isp*`, `wt-ane`, `wt-extdisp`, `wt-periph`, `wt-platform`, old bases), and against the
driver match tables. DRIVEN = DT node at that register address and a driver that matches one of its compatibles;
PREPARED = DT node only in a test worktree; DRIVER-ELSEWHERE = a family driver exists but no T6050 node or match;
NO-DRIVER = nothing in any Linux tree; FIRMWARE-ONLY = pmgr placeholders, debug/trace, memory-controller internals,
exclave plumbing. Only names, compatibles, property names and `reg` offsets/sizes were read into the working files;
none of those files is committed.
