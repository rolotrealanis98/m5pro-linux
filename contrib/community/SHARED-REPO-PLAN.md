# A shared tracker for Linux on M4+ Macs: plan

Status: proposal for review, 2026-11-08 (UTC). Nothing has been created yet: no organisation, no repository, no
invitations. Written in answer to TripleU613's two requests on
[omacom/linux-aurora #293](https://github.com/omacom/linux-aurora/issues/293) (a status repo per machine, and "a shared
repo or integration branch for Linux Aurora / Apple Omarchy M4+ where everyone can contribute: a common place for
patches, tested builds, and status") and Rolando's reply there that he would set one up. The ready-to-post comment is
section 7.

## Executive summary

M4/M5 bring-up is spread over at least eight places: `aurora-silicon/linux` and `aurora-silicon/m1n1`,
`omacom/linux-aurora`, `omacom/m1n1`, `omacom/omarchy-mac-pkgs`, edimoldovan's J714c forks (`linux-aurora`, `m1n1`,
`u-boot`, `kernel`), TripleU613's `Omarchy-M5-Pro` (J714s), betizzel's `omarchy-m5` (J714s), and this repo (J716s).
Several of these solve the same problem on the same SoC (T6050) without knowing it. We need one place that **tracks,
documents and points**. It should not hold code.

Proposal:

- **One tracker repo** in a new, neutral GitHub organisation, with several owners from the start, one for each machine.
  It holds a status matrix (machine x feature), dated result logs, tested build *recipes* (hashes, never binaries), and
  topic notes that apply to every machine (boot chain, m1n1, kernel subsystems, GPU, display, audio, Wi-Fi, power).
- **Code stays upstream.** Kernel work goes as PRs to `omacom/linux-aurora` and `aurora-silicon/linux`, loader work to
  `omacom/m1n1` and `aurora-silicon/m1n1`, packages to `omacom/omarchy-mac-pkgs`. The tracker indexes those PRs and their
  state. Per-machine patch queues are allowed only as read-only mirrors, each with its provenance and an upstream target.
  There is no integration branch here.
- **The data is machine-readable.** Each machine has one YAML file. CI validates it, generates the README tables and a
  static site (GitHub Pages), checks the links, and scans for serials, MACs, secrets and binaries. Every "works" cell
  must link to a result log from that machine.
- **Docs live in the repo, not in a GitHub wiki**, so every change is a reviewed PR. Asahi made the same move: its
  feature-support pages started as GitHub wiki pages and now live as Markdown in `AsahiLinux/docs`, built by CI and
  served through GitHub Pages.

**Top three recommendations**

1. **Independent org, several owners.** For example `m4plus-linux/tracker`, with Pages at `m4plus-linux.github.io`. The
   owners are the people with the machines: J716s (rolotrealanis98), J714c (edimoldovan), J714s (TripleU613,
   betizzel). If the omacom or Aurora maintainers want it, the repo can be transferred to them later (section 2.1).
2. **Evidence-gated, machine-readable status.** One YAML file per board is the single source. A state needs a dated
   result file with log lines, and the validator refuses anything else. "Reproduced" is computed from a second setup.
   Stale cells are flagged automatically.
3. **Track and point, never fork.** No kernel or loader branches. Mirrors carry their provenance and are checked by CI.
   No binaries anywhere, only hashes. A privacy scanner runs on every PR. The tracker links each board's omacom per-Mac
   test-report issue instead of competing with it.

## 1. Scope and non-goals

### In scope

| What | Form |
|---|---|
| Status per machine | `machines/<board>/machine.yaml`, rendered into a matrix (README and site) |
| Result logs | `machines/<board>/results/YYYY-MM-DD-<slug>.md`, one run per file, scrubbed log excerpts |
| Tested builds | `builds/<board>/<name>.yaml`: the recipe (upstream repos, commits, patch lists, config, boot args) plus the full sha256 of every ingredient and output. Never the binary |
| Payload recipes and boot procedures | `topics/boot-chain/` (stub, firmware versions, stage 1/2, A/B fallback, recovery) |
| Cross-machine knowledge | `topics/<area>/`: what is known per SoC, open questions, links to the PRs |
| Upstream PR index | `upstream/prs.yaml` (hand-written: repo, number, machines, features), plus `upstream/status.json` (generated by a bot: open, merged, closed, review state) |
| Help wanted | Issues labelled `help-wanted`, produced from gaps in the matrix |
| Per-machine patch mirrors (optional) | `machines/<board>/patches/` only with `PROVENANCE.yaml` (source repo, commit, author, licence, upstream PR or target). Read-only copies for people who need a single place to fetch from |

### Non-goals

- **No code development.** There are no kernel, m1n1, U-Boot or Mesa branches. An "integration branch" request is
  redirected: Omarchy's T6050 base is `omacom/linux-aurora` #404 (kernel) and `omacom/m1n1` #30 (loader). The J716s
  stacks on them as #413 and #33-#37, and Aurora's `integration/aurora` carries the driver work they pull from.
- **No binaries:** no payloads, kernels, DTBs, initramfs, rootfs images, Apple boot objects or firmware.
- **No installer or distribution.** The Omarchy installer is `omacom/omarchy-mac-installer`, and Aurora's catalogs are
  `aurora-silicon/aurora-distributions`.
- **No replacement for personal lab notebooks.** Personal status repos (this one, TripleU613's, betizzel's) stay as the
  detailed record. The tracker carries the summary and links into them.
- **No support forum.** Use GitHub Discussions in the tracker for questions. Bugs in a component go to that component's
  repo.

## 2. Structure

### 2.1 Where it lives

| Option | Pros | Cons |
|---|---|---|
| **A. New independent org** (recommended) | Neutral between omacom and Aurora Silicon, whose downstream projects (Omarchy, Aurora Fedora/Alarm/NixOS) all consume the same T6050 work. Owners can come from any camp. Nobody waits on another org's admins: omacom's roadmap shows one migration on hold for "GitHub administrator access" (#71). Pages, Actions and branch protection are free for public repos. Repo transfer later keeps issues, PRs and stars, and GitHub redirects the old URLs | One more name to learn. Discoverability depends on links from #293, Aurora discussion #142 and the personal status repos. We must keep it alive ourselves |
| B. Repo under `omacom` | Omarchy users find it. It sits next to linux-aurora and m1n1. The vouch/CI model is already there | Write access needs omacom membership, granted by its admins. Scope reads as Omarchy-only, although Aurora's distributions run the same kernels. It depends on an admin bottleneck that already exists |
| C. Repo under `aurora-silicon` | The driver work lives there. Wiki and Discussions are already on | The same admin dependence. It reads as Aurora-only, and Omarchy users may not look there |
| D. Personal repo (status quo) | Zero setup | One owner, no shared write access, and it reads as one person's project. This is the situation TripleU613 asked to move away from |

**Recommendation: A**, with a standing offer in the README: "If omacom or Aurora Silicon want to host this, the owners
will transfer it." Name candidates: `m4plus-linux` (org) with the repo `tracker`, or `m4m5-linux` / `m5-linux`. All
three were unused on GitHub on 2026-11-08 (checked read-only with `gh api users/<name>`). Avoid "Apple", "Asahi",
"Omarchy" and "Aurora" in the name: they are other people's marks and projects.

Board ids are the directory keys (`J716s`, not marketing names). The marketing name, the `MacNN,N` identifier and the
SoC are fields in `machine.yaml`, so a search by any of them works on the site.

A topic page describes the problem once for a SoC: what the hardware does, which patches solve it, where they are
upstream, and which machines have confirmed it. Machine pages only say what happened on that machine. This split
keeps one fact from being written up separately for each machine, which is the duplication TripleU613 saw across "at
least 20 people".

### 2.3 The status matrix

**Two separate questions, two separate fields.** Asahi's feature-support tables answer "where is the code": a cell
holds a kernel release (merged upstream), `linux-asahi` (in their downstream tree), `WIP` or `TBA`, and only a few
cells link to notes. During bring-up the question that matters first is "has it run on this machine, and how sure are
we". So each cell carries:

- **`state`**, the hardware state. It needs evidence:

| State | Meaning | Evidence required |
|---|---|---|
| `works-daily` | Part of the payload the owner boots day to day | A result file from this board, plus the build recipe it ran |
| `works-test` | Passed on a test payload or test tree, not in the daily yet | A result file from this board |
| `attended` | Built. The next step needs a person at the machine (cold start, listening test, plug test) | Recipe or patch link, plus what the attended step is |
| `prepared` | Patches or DT written, not booted | Link to the patches or PR |
| `blocked` | Tried and failed, or needs something not available (firmware, documentation, hardware) | A result file or issue saying what blocks it |
| `not-realistic` | Not planned (for example Touch ID behind the Secure Enclave) | One sentence of reason |
| `untested` | Default. Nothing known | None |

- **`kind`** of the evidence, using TripleU613's labels so their repo maps over without loss: `native` (run on this
  board by this setup), `reported` (someone else's claim, not yet reproduced here), `offline` (built and reviewed, not
  run). Only `native` evidence can support a `works-*` state. A `reported` claim shows as a footnote on the cell, not
  as the state.
- **`upstream`**, where the code is. Each entry is a PR reference with its live state from `upstream/status.json`:
  `merged` (with tree and tag), `open`, `held`, or `none` (not submitted). This is Asahi's dimension, kept beside the
  hardware state, not mixed into it.
- **`reproduced`** (computed, not written): true when two setups (two people, or two boards of the same SoC) have
  `native` evidence for the same feature. The site marks these cells.
- **`verified`**: the date of the newest supporting result. CI flags the cell as stale (section 4) when this date is
  too old.

Rendering: the cell text is the state label. The tooltip or drill-down shows the evidence links, the upstream PRs and
the date. Colour is never the only signal: every cell has its text label.

Asahi split its single feature page into one page per chip generation once the device list grew too long. The site
should do the same from the start: one matrix page per SoC family (M4, M5), with machines as columns.

### 2.5 Docs in the repo, not a wiki

**Decision: docs in the repo, published with GitHub Pages. The GitHub wiki is disabled.**

- Wiki edits are not PRs. Nobody reviews them, CI cannot validate them, the privacy scanner never sees them, and
  CODEOWNERS cannot route them to a machine's owner.
- A wiki lives in a separate git repo. It cannot be changed in the same PR as the YAML it describes.
- Precedent: Asahi's feature-support and device pages started on the `AsahiLinux/docs` GitHub wiki (the "M1/M2/M3
  Series Feature Support" pages). They now live as Markdown under `docs/platform/feature-support/` in that repo. The
  site "is rebuilt by the CI on every commit and served via GitHub Pages" at asahilinux.org/docs.
- GitHub Discussions stays on for questions and loose notes that are not yet facts.

### 2.6 Result logs

One run per file, never edited after merge except to add a `Correction` section at the end (TripleU613's
"claims that turned out wrong are corrected in place" practice, made explicit). File name:
`results/YYYY-MM-DD-<slug>.md`, dates in UTC.

```markdown
---
date: 2026-11-07T23:16Z
board: J716s
setup: rolo-aurora73
build: builds/J716s/daily-n1k-20261107.yaml     # or an inline recipe for a one-off
build_sha256: 512a1c00...                        # full hash in the real file
firmware: { os: "27.3 beta 1 (26C5035r)", system: "27.3 beta 1 (26C5035r)" }
attended: false                                  # true when a person was at the machine; say what they did
source: https://github.com/rolotrealanis98/m5pro-linux/blob/<commit>/contrib/validated/integration/RESULTS.md#daily-n1k-...
features: [cpu.smp, wifi-bt.wifi, wifi-bt.bt, gpu.vulkan]
---

## What was booted
## Results
| Feature / action | pass, fail, not tested | Detail |
## Log excerpts (scrubbed)
## Not tested
```

The rules come from the omacom/Aurora reporting guide, so a result written here can be pasted into the board's omacom
test-report issue unchanged. Report both firmware fields. Give pass, fail or not tested for each action. Quote error
lines literally, trimmed, never whole journals. List what was not tested. A driver probe is not a pass. Links into a
personal status repo point at a commit (a permalink), so they survive later rewrites there.

## 3. Governance and contribution rules

### 3.1 Roles and merging

- **Owners** (org admins, 3 to 5 people, from at least two different machines): repo settings, schema, CI, policy.
  Initial set: rolotrealanis98, edimoldovan, TripleU613, betizzel (if they accept). Rolando already offered
  TripleU613 and edimoldovan moderator rights on #293.
- **Board maintainers** (CODEOWNERS for `machines/<board>/`): the people with that machine.
- **Topic maintainers** (teams): whoever is doing the work in that area. They are added by an owner once someone asks.
- **Merge rules** (branch protection on `main`, required checks, squash merge, no force push, no direct pushes,
  owners included):
  - `machines/<board>/`: one approval from that board's maintainer. If the PR author is the only maintainer, any other
    maintainer approves (a second pair of eyes for the privacy check).
  - `topics/`: one topic maintainer, or any two board maintainers.
  - `schema/`, `tools/`, `.github/`, `POLICY.md`, `GOVERNANCE.md`: two owners.
  - `upstream/status.json`: only the bot, through a PR that a maintainer merges.
- **Changing the rules:** an issue labelled `type:policy`, open at least 7 days, a majority of owners in favour.
- **Inactivity:** a board with no merged change in 60 days shows `unmaintained` on its page (its data stays). An owner
  inactive for 90 days is asked, then moved to emeritus.

### 3.2 How a result is accepted

1. A state change PR must link a result file from the same PR or one already merged. The validator rejects a
   `works-*` state without `native` evidence.
2. The result file carries a log excerpt for each pass line, or a clear statement of what a person saw or heard
   (attended checks: a tone heard, the lid woke the machine). Both are acceptable. "It works" without either is not.
3. A claim that a fix "applies to" another board is entered on that board as `kind: reported`, with a link. It becomes
   `native` only with a result from that board.
4. `reproduced` needs two independent setups. It is computed, never claimed by hand.
5. The board maintainer can refuse a result they cannot reconcile with their machine. The disagreement stays visible as
   two setups with different states.

### 3.3 Licensing

| Material | Licence | Why |
|---|---|---|
| Prose (`README`, `topics/`, `NOTES.md`, results text) | **CC-BY-SA-4.0** | Keeps derived wikis and forks open. Asahi's docs use CC BY 3.0. A share-alike licence fits a community knowledge base where several projects copy from each other |
| Data (`machine.yaml`, `builds/`, `upstream/prs.yaml`, result front matter) | **CC0-1.0** | Lets omacom's catalog, Aurora's validation evidence or an installer pull status with no attribution machinery |
| Tools (`tools/`, workflows) | **MIT** | Same as m1n1 and most of the ecosystem's tooling |
| Mirrored patches | **Their own licence**, SPDX in every file (kernel GPL-2.0-only or per file, m1n1 MIT) | Not relicensed. They must be upstream-bound (`PROVENANCE.yaml` names the upstream PR or target repo) and carry the human author's `Signed-off-by` |

Source repos with no licence are linked, never mirrored, unless the author adds a licence or gives written permission
in the PR: betizzel's `omarchy-m5` has none (an MIT LICENSE was added and removed on 2026-10-10), and TripleU613's
`m5-omarchy/` says "all rights reserved" until it has one. A contribution PR states that its text is offered under the
licence of the path it touches. CONTRIBUTING says so, and the PR template repeats it.

### 3.4 AI assistance

The projects around this work disagree, so the repo must state its own rule and the rules of each destination:

- **Asahi Linux** forbids generative AI in any contribution, and repeat violations draw a permanent ban
  (asahilinux.org/slop). TripleU613 notes that upstream `AsahiLinux/m1n1` asks AI tools not to use it.
- **aurora-silicon/linux** follows the kernel's `Documentation/process/coding-assistants.rst`: an
  `Assisted-by: LLM [TOOL...]` tag, and only humans add `Signed-off-by`.
- **omacom** repos do not require a tag. Their CONTRIBUTING does not mention AI. The same in-tree kernel document is
  present in `omacom/linux-aurora`.

Proposed `POLICY.md` text:

> **AI assistance.** Contributions made with AI tools are accepted. Every PR has a human author who has read it and
> answers for it. A hardware result must come from a real run on the named machine, never from a tool's summary of what
> should have happened. This repository does not require disclosure trailers. Mirrored patches keep whatever their
> destination requires: `Assisted-by:` for aurora-silicon, nothing for omacom unless its maintainers ask. **Nothing in
> this repository is submitted to Asahi Linux**, and material here should be treated as AI-assisted for the purposes of
> Asahi's policy. If you contribute to Asahi, do not copy from this repository.

This is a decision for the owners. The alternative is mandatory disclosure (a PR checkbox), which costs little and
matches Aurora's rule. Choose one before the repo opens, and do not leave the policy implicit.

### 3.5 Privacy

Never in the repo, in any form (CI rejects what it can detect):

- serial numbers, ECID, nonces, the boot-security parts of `/chosen`, MAC and Bluetooth addresses, IP addresses
  (including LAN and VPN), host names, user names and home paths in logs, account details;
- Apple firmware, boot objects (kernelcache, SPTM, TXM), per-unit firmware (the N1 Wi-Fi/Bluetooth image), calibration
  bytes, NVRAM dumps, raw device trees read from a running machine (`/proc/device-tree`), core dumps;
- **full ADT dumps, even redacted.** birkskyum's #293 attachment follows a good practice (serials, MACs, nonces and the
  ECID removed, with a `removed.txt` listing every removed property), but a full dump is too much to review in a PR.

**How to share ADT-derived facts:** quote the specific node and property names and the values that are the same on
every unit of the board: register addresses and sizes, compatible strings, power-domain ids and flags, interrupt
numbers, clock rates. Edimoldovan's PMGR table on #293 (device, flags, id, offset) is the model. For a value that might
be per unit (tunables, voltage or calibration tables), say so and give the property name. Publish the value only after
two units of the same board show the same value. Otherwise point to the code that reads it at boot (this repo's m1n1
0021 fills the PHY tunables from the ADT at boot for exactly this reason).

### 3.6 Security

- **No binaries.** CI rejects files by extension and by content type (Mach-O, ELF, gzip/zstd/cpio, DTB magic `d00dfeed`,
  FAT/APFS images) and any non-text file over 256 KiB. Screenshots are allowed as PNG/JPEG under that limit, and are
  reviewed for private data.
- **Hashes only:** full sha256 (no prefixes) for every ingredient and output in `builds/`. A short prefix may appear in
  prose for readability, next to the full hash in the YAML.
- **No download links** to unofficial binaries in recipes. Every ingredient is an upstream commit, a tagged release of
  a signed package, or a patch in a public repo.
- **Workflows:** default `GITHUB_TOKEN` read-only, actions pinned by commit SHA, no `pull_request_target` with checkout
  of PR code. The bot writes through PRs, never to `main` directly.

## 4. Automation

| Workflow | Trigger | What it does |
|---|---|---|
| `validate.yml` | every PR and push | Schema check of every `machine.yaml`, result front matter and build file (`check-jsonschema`). Feature ids exist in `features.yaml`. Each `works-*` cell has `native` evidence whose file and anchor exist. Every `upstream` ref is in `prs.yaml`. `tools/gen.py --check`: the generated README tables match the YAML, and the contributor runs `make gen`. Internal link check plus `lychee` for external links (warnings only, so a flaky site does not block). `privacy_scan.py` (below). `gitleaks` for tokens and keys. Binary rejection (3.6). Mirror check: every `patches/` series has `PROVENANCE.yaml` with source, commit, licence and an upstream PR or target |
| `pages.yml` | push to `main` | Builds the site (per-SoC matrix pages, machine pages, topics, an upstream PR dashboard) and deploys it to Pages |
| `stale.yml` | weekly | Marks cells as stale when `works-daily` is older than 30 days, `works-test` older than 21 days, or the setup's `current_build` changed after the newest evidence. Opens or updates one `stale` issue per board, assigned to its maintainers |
| `upstream-sync.yml` (optional) | every 6 h | Reads `upstream/prs.yaml`, queries the GitHub API (public read) for each PR's state, merge commit, last update and review decision, and writes `upstream/status.json` in a bot PR. When a PR merges, it adds `upstream:merged` to the cells that cite it so their maintainer can update the note |
| `labels.yml` | push touching `.github/labels.yml` | Syncs labels |

**The privacy scanner** (`tools/privacy_scan.py`, regex plus allowlist, runs on the diff):

- MAC and Bluetooth addresses: six hex octets, colon- or dash-separated.
- IPv4 outside the documentation ranges (192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24), and IPv6 outside 2001:db8::/32.
- `serial-number`, `mlb-serial-number`, `ecid`, `nonce`, `apnonce`, `boot-nonce`, `mac-address`,
  `local-mac-address`, `wifi0`/`bluetooth0` address properties with a value next to them.
- Apple serial patterns after "Serial" (10 to 12 uppercase alphanumerics).
- `/Users/<name>`, `/home/<name>` and `user@host` prompts, unless they match an allowlisted placeholder (`<user>`,
  `<host>`).
- Hex runs over 64 bytes in a results file outside a fenced block marked `hexdump-reviewed`.

A failure says which line matched and how to scrub it. The scanner also runs locally (`make check`), so it catches the
problem before a push.

Kernel builds are not bit-reproducible by default. The recipe records `KBUILD_BUILD_TIMESTAMP`, `KBUILD_BUILD_USER`,
`KBUILD_BUILD_HOST` and the toolchain versions used, so a rebuild can be compared. A mismatched hash is reported, not
hidden.

**Optional later:** a small client in the spirit of `aurora-diag report` (Aurora's bring-up tool, which writes "one
JSON plus text file to attach to a bug") that turns a run into a result-file skeleton. Its output still goes through
the scanner: we have not checked whether `aurora-diag` itself scrubs identifiers.

## 6. Risks and how the design handles them

| Risk | Design answer |
|---|---|
| **Fragmentation:** the tracker becomes the ninth place to look | It holds no code, so there is nothing to keep in sync with the upstream repos. Every cell points to the PR and to the board's personal status repo. It links each board's omacom per-Mac test-report issue, and its result format pastes into that issue unchanged. It is announced where people already are (#293, discussion #142) and offered for transfer to omacom or Aurora |
| **Stale status** | Each cell carries `verified`, a weekly job flags old cells and a changed `current_build`, a maintainer is assigned per board, and a board with no change in 60 days shows `unmaintained`. The site shows dates next to states |
| **Scope creep into a kernel fork** | POLICY.md: no branches of kernel, loader or Mesa. Mirrors are allowed only with `PROVENANCE.yaml` naming an upstream PR or target, and CI checks that. "Integration branch" requests get the standing answer in CONTRIBUTING: omacom #404/#413 and #30/#33-#37, and Aurora `integration/aurora` |
| **Claims inflation** (a probe counted as "works") | `features.yaml` defines "works" per feature. `works-*` needs `native` evidence. `reported` claims never set a state. `reproduced` is computed |
| **Privacy leak** | Scanner plus `gitleaks` on every PR, binary rejection, no full ADT dumps, a maintainer review on every board PR, a privacy checklist in the PR template. If a leak is merged anyway: rewrite history and ask GitHub support to purge cached views. The procedure is written down in POLICY.md before day 1 |
| **Licence contamination** (unlicensed sources, or clean-room projects) | Unlicensed repos are linked, never copied. Mirrors carry SPDX and provenance. The AI section tells Asahi contributors not to copy from here |
| **Owner bus factor** | 3 to 5 owners from different machines from day 1. The org outlives any one person's interest |
| **Maintainer burden** | Generated README and site, schema validation and the stale job do the routine work. Humans review evidence and privacy, nothing else |
| **Trademark and identity** | The name avoids other projects' marks. The README says the tracker is independent of Apple, Asahi Linux, Omarchy/omacom and Aurora Silicon |
