kboot: train the T6050 N1 link and fill its hand-off (J716s Wi-Fi/Bluetooth)

iBoot does not train apcie0 port 0 on the J716s (MacBook Pro 16-inch, M5 Pro, T6050), so the N1 Wi-Fi/Bluetooth module never appears to Linux. linux #937 adopts a root port only if the boot loader trained it, and #938's centauri driver needs the firmware name, platform ID and port tunables that only the ADT holds. This series does both in m1n1:

1. `kboot: n1: fill the T6050 N1 hand-off in the DT` (`kboot_n1.c`): for an `apple,t6050-pcie` host, the N1 control function (`pci106b,1900`) gets `firmware-name = "apple/centauri/<target-type>-ftab.bin"`, `apple,centauri-platform-id` (board-id << 16 | chip-id) and `apple,centauri-protocol = <27>`. Each `apple,link-trained-by-bootloader` root port gets the ADT `pci-bridge<n>` config, rc and gen3/4/5 shadow tunables. The root port and its DART are enabled only if the link is up the way the adoption needs it. Otherwise both stay disabled, because the DART of a port that is not up takes an SError. This patch trains nothing.
2. `pcie: t6050: train apcie0 port 0 (the N1) behind chosen.asahi,t6050-n1` (`pcie_t6050.c`): Aura's T6050 GP-port bring-up from aura #60/#61 (Jeff Queisser, measured on J775D port 2), ported to port 0. Every address comes from the ADT. Before and after each stage that touches the shared GP PHY, the storage registers (ANS, NVMe, SART, power) are compared with a reference, and any change stops the training. This patch also adds `tunables_check_local_addr()`, `pmgr_psreg_by_name()` and `kboot_get_chosen()`, and `pmgr_power_is_on()` now skips virtual devices (T6050 has a no_ps `APCIE_PHY_SW` beside the real one).
3. `pcie: t6050: start ANS for the N1 training's storage checks`: if a stage-1 stopped ANS, the storage check cannot run. This patch starts ANS with `nvme_init()` and reads the GPT header. After the training it requires the same registers and the same block, then hands storage on with `nvme_shutdown()`. If storage is in doubt, it resets through the watchdog instead of booting a kernel that cannot mount its root. The RTKit HELLO/endpoint-map wait becomes settable (still 1 s by default). The training uses 10 s, because this ANS can take about 3 s to answer after a stop.
4. `pcie: t6050: pulse the N1 reset through the SMC as on J813`: `pci-bridge0 function-reset` on the J716s is `pKW4("gP13", 0x00800000)`, the same descriptor aura's `j813_n1.c` uses. The patch writes template | 0, waits 50 ms, writes template | 1 and waits 50 ms, then waits 100 ms before the port reset. The link-up wait is 1 s.

Opt-in values of `chosen.asahi,t6050-n1`:
- `1`: train only.
- `2`: SMC reset pulse, then train.
- `3`: `1` with ANS started for the storage checks.
- `4`: `2` with ANS started for the storage checks. This is the mode that brings the N1 up.
- `5`: `4` with J813's port order. Untested.

If the variable is unset, nothing is trained, and a root port that is not up stays disabled.

**Tested on:** J716s, with the same four changes on our own m1n1 lineage (AsahiLinux m1n1 plus SPTM and T6050 bring-up). Boot chain: an A/B chainloading stage-1, then a stage-2 that runs kboot. Kernel: aurora `integration/aurora` plus the T6050 series (#935/#937/#938/#945).
- **No variable:** iBoot leaves port 0 untrained (`ltssm 0x0`, `linksts` bit 0 clear). The root port and its DART stay disabled, and Linux boots normally.
- **`=1`:** refused by its own guard: "ANS is not running (before)". Our stage-1 stops ANS.
- **`=3`:** m1n1 started the stopped ANS, read the GPT header, ran stages A and S with storage unchanged, and stopped ANS again. NVMe was fine in Linux. The link did not come up within 500 ms because the N1 was still held in reset.
- **`=4`:** after the SMC `gP13` pulse, the port trains at Gen1 x1. The endpoint at `01:00.0` is `106b:1900`, the block read-back is identical, and Linux logs `adopted port 0, endpoint 01:00`.
- **FTAB:** with the bundle FTAB as is, the N1 ROM rejects the image (`phase0: -5`). The board's Image4 manifest has to be stitched into the FTAB's ticket slot: header 0x10/0x14 = ticket offset/length, IM4M after the last entry. With that, the ROM accepts the image and `[106b:1902]`/`[106b:1903]` appear. The Wi-Fi firmware reports 2.4 and 5 GHz channels, and `wlan0` and `hci0` register. A scan sees 55 BSSes, and `btmgmt find` sees 36 devices. With wpa_supplicant it associates to a WPA2 5 GHz network, gets a DHCP lease and passes traffic (17 ms pings).
- **ASPM:** the N1 boot that brought up Wi-Fi ran with `pcie_aspm=off` in the kernel. With ASPM on, it froze about 30 s after login, as edimoldovan saw on the J714c. A pcie-apple patch that keeps ASPM off on adopted ports will follow separately once it has been booted.

**Rebased onto `aurora-wip`, build-tested only:** this branch has not been booted. It builds clean at each of the four commits: plain `make -j8`, Fedora 43 clang/lld 21.1.8, rustc 1.99.1, 15 warnings, the same as the base, none new; `clang-format` clean on the new files. Two differences from what was tested:
- On `aurora-wip`, `nvme_shutdown()` leaves an M4-class ANS running with its controller disabled (`nvme_adopt_live_session`), where our lineage stopped it. So with `=3`/`=4`, Linux gets a running ANS instead of a stopped one. The code accepts either; only an `nvme_shutdown()` failure counts as storage lost.
- `pmgr_power_is_on()` now skips virtual devices. Its other callers query `DISPEXT0_CPU`.

**Base:** `aurora-wip` (`b6b4592`), not `main`. `main` is an ancestor of `aurora-wip`, 353 commits behind, and recent PRs (#57-#64) target `aurora-wip`.

**Dependencies:**
- Kernel: #937 (adopts the root port the loader trained), #938 (centauri), #945 (the J716c DT style with `apple,link-trained-by-bootloader` on port 0).
- Firmware: the FTAB with the manifest stitched in must come from the distro or installer, not m1n1. It is per board and per macOS build, but not per unit: the manifest has no ECID or nonce.
- Bring-up: `aurora-wip` has no other T6050 support beyond CPU IDs and SMP, so a J716s boot of this exact tree is unverified.

**Not tested yet:**
- Warm reboot with the N1 link alive. The J714c needed a pcie-apple shutdown park; every test here started from a full power-off.
- `=5` (J813 port order).
- Other T6050 boards (J714s, J716c); the code takes everything from the ADT.
- Image size: the plain image's file part grows from 0x110000 to 0x120000, exactly `m1n1-raw.ld`'s `_file_limit`, with no room left. `CHAINLOADING=1` already fails that assert on the base (0x130000), so this series does not change that.

**Open questions:**
- Does this belong in aura instead? Aura has `j813_n1.c` and `j813_n1_prepare()`, and the training itself comes from aura's T6050 work (#60/#61). Aurora's m1n1 has no other T6050 support. Glad to move it.
- Gate by chip/board like `j813_n1_prepare()` (T6050 plus an okay host node, no opt-in), or keep the `chosen.asahi,t6050-n1` opt-in until more T6050 boards have run it? If it stays opt-in, is the name right? I followed `asahi,t6030-gpu` and `asahi,j713-dcpext`.
- Collapse the modes to one (`=4`)? `1`/`2`/`3`/`5` only exist for bring-up comparisons.
