kboot: train the T6050 N1 link and fill its hand-off (J716s Wi-Fi/Bluetooth)

iBoot does not train apcie0 port 0 on the J716s (MacBook Pro 16-inch, M5 Pro, T6050), so the N1 Wi-Fi/Bluetooth module never appears to Linux. linux #937 adopts a root port only if the boot loader trained it, and #938's centauri driver needs the firmware name, platform ID and port tunables that only the ADT holds. This series does both in m1n1:

1. `kboot: n1: fill the T6050 N1 hand-off in the DT` (`kboot_n1.c`): for an `apple,t6050-pcie` host, the N1 control function (`pci106b,1900`) gets `firmware-name = "apple/centauri/<target-type>-ftab.bin"`, `apple,centauri-platform-id` (board-id << 16 | chip-id) and `apple,centauri-protocol = <27>`. Each `apple,link-trained-by-bootloader` root port gets the ADT `pci-bridge<n>` config, rc and gen3/4/5 shadow tunables. The root port and its DART are enabled only if the port meets the adoption's preconditions:
   - root complex running, port ready, link up and not retraining, LTSSM on
   - an Apple endpoint behind the port
   - no RID route yet
   - the endpoint's I/O, memory and bus-master bits clear
   - the DART's protection and stream registers still 0

   Otherwise both stay disabled, because the DART of a port that is not up takes an SError. This patch trains nothing.
2. `pcie: t6050: train apcie0 port 0 (the N1) behind chosen.asahi,t6050-n1` (`pcie_t6050.c`): Aura's T6050 GP-port bring-up from aura #60/#61 (Jeff Queisser, measured on J775D port 2), ported to port 0. Every address comes from the ADT.
   - Storage registers (ANS, NVMe, SART, power) are compared with a reference before and after each stage that touches the shared GP PHY.
   - A failed check before the training only refuses it. A change after a stage returns `N1_STORAGE_LOST`, and m1n1 then resets the SoC through the watchdog instead of booting.
   - Any other stop keeps port 0 and its DART disabled, even if the link came up.
   - This patch also adds `tunables_check_local_addr()`, `pmgr_psreg_by_name()` and `kboot_get_chosen()`, and `pmgr_power_is_on()` now skips virtual devices (T6050 has a no_ps `APCIE_PHY_SW` beside the real one).
3. `pcie: t6050: start ANS for the N1 training's storage checks`: if a stage-1 stopped ANS, the storage check cannot run.
   - This patch starts ANS with `nvme_init()` and reads the GPT header.
   - After the training it requires the same registers and the same block, then stops ANS again with the new `nvme_stop()`.
   - On M4 and later, `nvme_shutdown()` leaves ANS, its RTKit session and its SART-mapped buffers live for a later stage to adopt. Nothing adopts them here: Linux's nvme-apple boots a stopped ANS itself. So `nvme_stop()` continues to the M1-M3 teardown, and no firmware-owned buffer is left in RAM that Linux sees as free.
   - The RTKit HELLO/endpoint-map wait becomes settable (still 1 s by default). The training uses 10 s, because this ANS can take about 3 s to answer after a stop.
4. `pcie: t6050: pulse the N1 reset through the SMC as on J813`: `pci-bridge0 function-reset` on the J716s is `pKW4("gP13", 0x00800000)`, the same descriptor aura's `j813_n1.c` uses. The patch writes template | 0, waits 50 ms, writes template | 1 and waits 50 ms, then waits 100 ms before the port reset. The link-up wait is 1 s.

Opt-in values of `chosen.asahi,t6050-n1`:
- `1`: train only.
- `2`: SMC reset pulse, then train.
- `3`: `1` with ANS started for the storage checks.
- `4`: `2` with ANS started for the storage checks. This is the mode that brings the N1 up.

If the variable is unset, nothing is trained, and a root port that does not meet the adoption preconditions stays disabled.

**Tested on:** J716s, with the same changes on our own m1n1 lineage (AsahiLinux m1n1 plus SPTM and T6050 bring-up). Boot chain: an A/B chainloading stage-1, then a stage-2 that runs kboot. Kernel: aurora `integration/aurora` plus the T6050 series (#935/#937/#938/#945).
- **No variable:** iBoot leaves port 0 untrained (`ltssm 0x0`, `linksts` bit 0 clear). The root port and its DART stay disabled, and Linux boots normally.
- **`=1`:** refused by its own guard: "ANS is not running (before)". Our stage-1 stops ANS.
- **`=3`:** m1n1 started the stopped ANS, read the GPT header, ran stages A and S with storage unchanged, and stopped ANS again ("nvme: shutdown done"). NVMe was fine in Linux. The link did not come up within 500 ms because the N1 was still held in reset.
- **`=4`:** after the SMC `gP13` pulse, the port trains at Gen1 x1. The endpoint at `01:00.0` is `106b:1900`, the block read-back is identical, ANS is stopped again, and Linux logs `adopted port 0, endpoint 01:00`.
- **FTAB:** with the bundle FTAB as is, the N1 ROM rejects the image (`phase0: -5`). The board's Image4 manifest has to be stitched into the FTAB's ticket slot: header 0x10/0x14 = ticket offset/length, IM4M after the last entry. With that, the ROM accepts the image and `[106b:1902]`/`[106b:1903]` appear. The Wi-Fi firmware reports 2.4 and 5 GHz channels, and `wlan0` and `hci0` register. A scan sees 55 BSSes, and `btmgmt find` sees 36 devices. With wpa_supplicant it associates (WPA2, 5 GHz), gets a DHCP lease and passes traffic.
- **ASPM:** the N1 boots ran with `pcie_aspm=off` in the kernel. With ASPM on, it froze about 30 s after login, as edimoldovan saw on the J714c. A pcie-apple patch that keeps ASPM off on adopted ports is sent separately.

**This exact branch:** built at each of the four commits: plain `make -j8`, Fedora 43 clang/lld 21.1.8, rustc 1.99.1, 15 warnings, the same as the base, none new; `clang-format` clean on the new files. The `=4` path runs the same register sequence and the same full ANS stop as the tested lineage. A J716s boot of this tree is pending; I will report it here. Two differences from the tested lineage:
- `aurora-wip` itself has never booted a J716s.
- `pmgr_power_is_on()` now skips virtual devices. Its other callers query `DISPEXT0_CPU`.

**Base:** `aurora-wip` (`b6b4592`), not `main`. `main` is an ancestor of `aurora-wip`, 353 commits behind, and recent PRs (#57-#64) target `aurora-wip`.

**Dependencies:**
- Kernel: #937 (adopts the root port the loader trained), #938 (centauri), #945 (the J716c DT style with `apple,link-trained-by-bootloader` on port 0).
- Firmware: the FTAB with the manifest stitched in must come from the distro or installer, not m1n1. It is per board and per macOS build, but not per unit: the manifest has no ECID or nonce.

**Not tested yet:**
- Warm reboot with the N1 link alive. It does not come back on the J716s yet: a restart from a running N1 boot fell back to the previous slot. The J714c needed a pcie-apple shutdown that parks the adopted port. Every passing test here started cold or from a boot without the N1.
- Other T6050 boards (J714s, J716c); the code takes everything from the ADT.
- Image size: the plain image's file part grows from 0x110000 to 0x120000, exactly `m1n1-raw.ld`'s `_file_limit`, with no room left. `CHAINLOADING=1` already fails that assert on the base (0x130000), so this series does not change that.

**Open questions:**
- Does this belong in aura instead? Aura has `j813_n1.c` and `j813_n1_prepare()`, and the training itself comes from aura's T6050 work (#60/#61). Aurora's m1n1 has no other T6050 support. Glad to move it.
- Gate by chip/board like `j813_n1_prepare()` (T6050 plus an okay host node, no opt-in), or keep the `chosen.asahi,t6050-n1` opt-in until more T6050 boards have run it? If it stays opt-in, is the name right? I followed `asahi,t6030-gpu` and `asahi,j713-dcpext`.
- Collapse the modes to one (`=4`)? `1`/`2`/`3` only exist for bring-up comparisons.
