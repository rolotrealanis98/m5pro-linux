pcie, kboot: T6050: optional N1 (Wi-Fi/Bluetooth) training and hand-off behind chosen.asahi,t6050-n1 (stacked on PR-1)

Base: PR-1 (`omacom/t6050-bringup`): #30 + the CI test fixes + the RVBAR relay. This PR adds five commits. Branch: `omacom/t6050-n1`.

This is optional. The training only runs when the payload sets `chosen.asahi,t6050-n1`. #30 does not train the N1: edimoldovan's J714c kernel trains the link itself, and we are testing that kernel-side training on the J716s now. If it works there, the DT fill-in (commit 1) is the only part a loader still needs to provide, and the training (commits 2-5) can wait or be dropped. I am posting the whole series because it is what brings the N1 up on the J716s today, including across restarts.

iBoot does not train apcie0 port 0 on the J716s (MacBook Pro 16-inch, M5 Pro, T6050), so Linux never sees the N1. Linux's pcie-apple adopts a root port only if the loader trained it, and the centauri driver needs the firmware name, platform ID and port tunables that only the ADT holds.

1. `kboot: n1: fill the T6050 N1 hand-off in the DT` (new `kboot_n1.c`). For an `apple,t6050-pcie` host:
   - The N1 control function (`pci106b,1900`) gets `firmware-name = "apple/centauri/<target-type>-ftab.bin"`, `apple,centauri-platform-id` (board-id << 16 | chip-id) and `apple,centauri-protocol = <27>`, if they are unset.
   - Each `apple,link-trained-by-bootloader` root port gets the ADT `pci-bridge<n>` config, rc and gen3/4/5 shadow tunables.
   - The root port and its DART are enabled only if the port meets the adoption's preconditions: the root complex is running, the port is ready, the link is up and not retraining, LTSSM is on, an Apple endpoint sits behind it, there is no RID route yet, the endpoint's command bits are clear, and the DART's protection and stream registers are still 0. Otherwise both stay disabled: the DART of a port that is not up takes an SError when Linux probes it.

   This commit trains nothing.
2. `pcie: t6050: train apcie0 port 0 (the N1) behind chosen.asahi,t6050-n1` (`pcie_t6050.c`). This ports Aura's measured T6050 GP-port bring-up (aurora-silicon/aura #60/#61, Jeff Queisser) to port 0. Every address comes from the ADT.
   - Storage registers (ANS, NVMe, SART, power) are compared with a reference before and after each stage that touches the shared GP PHY. Once a valid reference exists, they are compared again whenever the training stops, including partway through a stage. A failed check before the training only refuses it. A change after that resets the SoC through the watchdog after 15 s, instead of booting a kernel that could not mount its root.
   - Any other stop keeps port 0 and its DART disabled.
   - Adds `tunables_check_local_addr()`, `pmgr_psreg_by_name()`, and `kboot_get_chosen()` (a wrapper around `kboot_chosen_param()` for other files). `pmgr_power_is_on()` now skips virtual devices, because T6050 has a no_ps `APCIE_PHY_SW` beside the real one. Its other caller queries `DISPEXT0_CPU`.
3. `pcie: t6050: start ANS for the N1 training's storage checks` (=3, =4). If ANS is stopped (our A/B stage 1 stops it after reading `boot.bin`), the training starts it with `nvme_init()` and reads the GPT header. Afterwards it requires the same registers and the same block, and stops ANS again with the new `nvme_stop()`. That is `nvme_shutdown()` continued through the M1-M3 teardown, so no RTKit session or SART buffer outlives the call. If ANS is already running, as in #30's Omarchy chain where stage 1 hands its live session to U-Boot (`asahi,nvme-adopt`), =3/=4 train as =1/=2 and leave ANS alone, so `nvme_adopt_live_session` and #30's marking are untouched. #30's opt-in coprocessor stop (`nvme_t6050_stop_coproc`, off by default) is checked before `nvme_stop()`'s teardown and wins when set. The RTKit HELLO wait becomes settable; it stays 1 s by default, and the training uses 10 s. Like the training, this runs once per boot: a second kboot preparation gets the first result and does not start a second ANS session.
4. `pcie: t6050: pulse the N1 reset through the SMC as on J813` (=2, =4). On the J716s, `pci-bridge0 function-reset` is `pKW4("gP13", 0x00800000)`, as on J813. The commit writes template | 0, waits 50 ms, writes template | 1, waits 50 ms, then waits 100 ms before the port reset. The link-up wait is 1 s.
5. `pcie: t6050: handle a warm N1 and a live port 0 at entry` (=2, =4). A restart resets the SoC but not the N1, which keeps running its firmware with gP13 released. With the SMC release:
   - The entry state and gP13 are printed.
   - A live link is parked first: LTSSM off, PERST# asserted, link down within 100 ms.
   - If gP13 reads released, the reset is held for 250 ms.
   - The endpoint must then answer in its ROM personality (106b:1900). An N1 that kept running (106b:1901) is never handed to Linux.
   - The SMC client gets bounded waits: each command, and the initialisation, has one 2 s deadline from the moment it is sent, which notifications do not extend ("SMC: no reply"). It also gets `smc_read_u32()`.

   This is what made restarts work on the J716s.

Values of `chosen.asahi,t6050-n1`:

| Value | Behaviour |
|---|---|
| 1 | train only |
| 2 | SMC reset pulse, then train |
| 3 | `1`, with ANS started for the storage checks |
| 4 | `2`, with ANS started for the storage checks; the mode that brings the N1 up |

Unset, nothing is trained, and a root port that does not meet the adoption preconditions stays disabled.

### Testing

MacBook Pro 16-inch, M5 Pro (J716s, Mac17,8), macOS 27.3 beta 1 stub (26C5035r, `mBoot-20457.60.65.0.1`). Boot chain: our A/B stage 1 chainloads a stage 2 that carries the kernel, DTB and initramfs. Kernel: integration/aurora with the T6050 series, the pcie-apple adopted-port patches (park on shutdown, ASPM off, link kept through s2idle) and centauri.

**This stack on hardware (2026-11-07).** The full stack on #30 (`omacom/wdt-keep` at 6653bb2, m1n1 `v1.6.1-429-g6653bb2`, before the review fixes) booted the J716s on the first pass, 74 s to SSH, with `chosen.asahi,t6050-n1=4`. The loader started ANS, pulsed gP13 and trained the N1 (`pcie-t6050: port 0 link Gen1 x1`, `port 0 up, N1 at 01:00.0`, `n1: port 0 up: root port and DART okay`). Linux had 18 CPUs, and Wi-Fi associated with Bluetooth up. The same stack on #26 had done the same earlier. The review fixes since (DT values kept, storage re-checked on a stop, the ANS path once per boot, one deadline per SMC command) have not booted. See PR-1 for one unexplained fallback on the warm restart after the session.

Earlier runs with the same code in our own stage 2 (under the name `chosen.m5pro,n1`), all on 2026-11-07:

| Run | Variable | Result |
|---|---|---|
| W0 | unset | iBoot leaves port 0 untrained (`ltssm 0x0`). Root port and DART stay disabled; Linux boots normally. |
| W1 | `=1` | Refused by its own guard ("ANS is not running (before)"); NVMe unaffected. |

| W4 | `=4`, with commit 5 | Three `systemctl reboot` cycles with wlan0 associated and a ping running: all three came back on the primary slot with the N1 adopted. A loader without commit 5 hung once on the warm N1, and the stage 1 watchdog booted the fallback. |
| daily | `=4` | Daily payload since then: 18 CPUs, N1 adopted, wlan0 and hci0. |

This branch:
- Boot-test payload rebuilt on #30: the daily's kernel, DTB and initramfs plus `chosen.asahi,t6050-n1=4`, self-test on. This loader disables the stage 1 watchdog (no PR-5), so the boot has to be attended.
- Each commit builds with `make` and `make CHAINLOADING=1`: no new warnings against #30. The image is still 0x410000 (plain) and 0x420000 (`CHAINLOADING=1`). CI's pytest set (Linux): all pass. `git clang-format`: clean.

Differences from the loader that was tested:
- **ANS**: #30's chain leaves ANS live for U-Boot; ours stops it. Commit 3 handles both, but only the stopped-ANS path has run on hardware.
- **#30's additions** (USB host prep, the PMP DAPF entry, live-ANS marking, the G17 GPU fill) were not in the loader that booted.

Dependencies:
- Kernel: pcie-apple adoption of a loader-trained port, and the T6050 centauri driver. The adopted-port shutdown park is what lets a restart reach m1n1 with the link parked.
- Firmware: the FTAB with the board's Image4 manifest stitched in comes from the distro or installer, not from m1n1. It is per board and per macOS build, not per unit.
