# Status, 2026-11-06: Linux on the 16-inch MacBook Pro M5 Pro (J716s, T6050)

One machine: MacBook Pro 16-inch, M5 Pro, Mac17,8, board J716s, SoC T6050, 18 CPU cores
(three clusters of six), 48 GiB. macOS 27.3 beta 1 (26C5035r) on both the main volume and the
Linux stub. Linux is Arch Linux ARM on the internal SSD, booted by a two-stage m1n1.

**How this was made.** The code, patches and reports in this repository were written with
Claude (an AI model) under Rolando's direction. Rolando ran every hardware test himself. Each
item below is labelled:

- **tested on hardware**: run on this Mac, with the result stated;
- **booted, not feature-tested**: the code was in a kernel that booted, but nobody has exercised
  the feature yet;
- **design only**: compile-checked at most, never run.

Asahi Linux does not accept AI-generated contributions. Nothing here is offered to Asahi as code.

## Open items

1. **schedutil never drops to the lowest step.** On R1-A, with `top` showing 99.2 % idle, the three
   policies sat at 2964000 / 2964000 / 1620000 instead of the minimum 1344000 / 1344000 / 1308000.
   A loaded cluster does reach 4308000 (cpu1, cpu7, cpu13). Suspects: `idle=nop` polling and
   frequency-invariance accounting. Needs the Studio to investigate.
2. **Which SMC patch cured the battery hang is unknown.** No bisect was done. Hypothesis only: the
   probe reads three 255-byte strings (`BMDN`, `BMSN`, `BMDT`) right before registering the
   battery, which makes patch 0018 (refuse a reply bigger than the read buffer) the leading
   suspect. Patches 0018-0027 are ports of the SMC/battery fixes in edimoldovan's linux-aurora.
3. **The notch is hidden.** The `asahi,show-notch` property is present under `/chosen`, but the
   current `m1n1-plain.bin` ignores it. Needs the m1n1 rebuild with the `kboot` show-notch patch.
4. **cpufreq tables and the E-cluster question.** `policy0` and `policy6` share a 14-step table
   1344000..4308000; `policy12` has a 16-step table 1308000..4308000. Recorded as is; which
   cluster is the efficiency cluster is still open.
5. **Keyboard backlight log line.** `leds_pwm led-controller: failed to read period for
   kbd_backlight, default to off` at boot. The backlight works anyway; the line is benign so far.
6. **Not yet run:** PMP dumps, A/B stage-1, s2idle, OPP-offset tools, ufw, lid `evtest`, USB host
   (R1-C). Two more payloads are ready for the next solo round: `R1-D` (battery on, no trace
   arguments) and `R1-E` (the same on the USB-host DTB).

## Findings

### SMP: the fix is in the stub's stage-2 mBoot

- Symptom on macOS 27.0-27.2 firmware: a released secondary powers up (PMGR ps 0x100 -> 0x1f0) but
  never fetches an instruction. This matches what others report on J714s and J714c.
- Apple's macOS 27.3 beta 1 release notes (26C5035r), mBoot > Resolved Issues: "Only a single core
  is available when you boot Linux or other third-party operating systems from a custom raw boot
  object on Mac computers with M5 Pro, M5 Max, and M5 Ultra chips. (182898702) (FB23916610)".
- Updating macOS on the main volume only updated LLB (`/chosen/system-firmware-version`).
  `/chosen/firmware-version` (stage 2) comes from the stub's Preboot restore bundle, which an
  update leaves alone, and secondaries still did not start. **The stub had to be recreated from
  27.3 beta 1** (`firmware-version` = `mBoot-20457.60.65.0.1`). After that, m1n1's existing T6050
  CPU-start code, with none of our patches touching it, started 17 of 17 secondaries over the
  proxy, and Linux came up with 18 CPUs.
- An in-place refresh of the stub fails at `bless` with bootpolicy error 11 ("AP boot mode"). An
  existing Permissive LocalPolicy can only be rewritten from 1TR, so recreate the stub instead.
- The untethered path needed three m1n1 patches on top of upstream `7cde7d1a`:
  - 0013: chainload relocates stage-2 above the T6050 secondary-only CTRR window, instead of
    refusing to load it in place;
  - 0014: `MAX_CPUS` 32 -> 24, which keeps the chainloading stage-1 under the iBoot size limit
    (below);
  - 0015: secondaries' RVBAR is locked to the stage-1 base. A relocated stage-2 plants a
    trampoline there and `/memreserve/`s it in the FDT. Without it the untethered boot had 1 CPU.
- Full log: `docs/smp-t6050-raw-path.md`. Boot excerpt: [`logs/01-smp-18-cpus.txt`](logs/01-smp-18-cpus.txt).

### Battery: the probe completes now

- R1-B, 2026-11-06: battery driver enabled, `macsmc_power.trace=1`. The trace shows probe start at
  7.877 s; reads `CH0R CHCE CHCC AC-i BSFC CHNC`; info queries `CHIS BITV B0RC B0RI B0RV CHTE CH0C
  CH0I BCF0`; writes `CH0K CH0B`; reads `CHWA` then `CHLS` (both keys exist); then `BMDN`/`BMSN`/
  `BMDT` (size 255) and `BNCB`. The battery registers at 8.834 s, the AC adapter at 8.893 s, the
  event notifier at 8.912 s, and the probe is done at 8.932 s (1.05 s in total). Afterwards
  `BITV`/`B0AV`/`BCF0` are read every 60 s; the trace budget runs out by itself ("budget used up,
  tracing off").
- Values while on MagSafe: Charging, health Good, capacity 81 %, 12.682 V, 3.525 A, charge now
  6574000 uAh of 8139000 full (8579000 design), cycle count 32, temperature 31.2 C, no
  time-to-empty on AC.
- MagSafe unplug and replug: `macsmc-ac` online 1 -> 0 -> 1, status Charging / Discharging /
  Charging. The SMC logs `aceElec: Elec Cause` lines on each event.
- Booted 3 of 3. Which of patches 0018-0027 removed the hang is not known (open item 2).

### Untethered two-stage boot

- iBoot raw image size: our plain stage-1 at 0x4D0000 boots. CHAINLOADING builds at 0x4E0000 and
  0x4F0000, with an unaligned appended variable, boot-looped into the "needs to be reinstalled"
  recovery. A 0x420000 build (`MAX_CPUS` 24), padded to a 64 KiB multiple after the variable,
  boots. **We did not separate size from alignment**, and some probes were confounded by the
  boot-failure counter (below). Similar size limits are reported on T8132 (bretttegart/j604-linux)
  and T8140 (aurora-silicon/m1n1 f24d7197).
- The `chainload=<ESP PARTUUID>;m1n1/boot.bin` variable has to be appended to the image, with a
  4-NUL terminator and padding to 64 KiB. Passing it as `chainload.py` arguments is ignored.
- `kmutil configure-boot` only works from the stub's paired 1TR recovery. The "Options" recovery
  fails with a code-pairing error.
- Recipe: `docs/boot-and-recovery.md` ("Untethered boot").

### NVMe: ANS sometimes needs ~3 s to answer

- The ANS RTKit firmware handed over by iBoot sometimes needs about 3 s to answer the RTKit
  handshake. `apple_rtkit_wait_for_completion` waits 1 s, so `nvme-apple` logs `ANS did not boot`
  / `Reset failure status: -62` and the root never appears. A manual rebind from the initramfs
  works.
- Patch 0016 raises the wait to 10 s. After that, NVMe came up at 8.3-10.7 s on every boot.
- This is a workaround: it changes the wait for every RTKit coprocessor, not just ANS.
- Patch: `contrib/pending/integration/patches/linux/0016-*`. Log: [`logs/03-nvme-ans-boot.txt`](logs/03-nvme-ans-boot.txt).

### Trackpad: the host drives the AFE reset

- MTP firmware AppleMTPFirmwareMac-6320.86.1 accepts the power-method-2 will/has requests but never
  drives the trackpad AFE (analog front end) reset, and never asks the host to.
- The ADT's `multi-touch` node has `function-afe-reset` pointing at the SMC PMU. Decoded, that is
  the SMC low GPIO bank, key `gp1c`, line 28, active-low.
- dockchannel-hid now does what macOS does: will(OFF), assert reset, 50 ms, has(OFF); then
  will(ON), release, 50 ms, has(ON). The GPIO is described on the multi-touch node. Without the
  property the driver keeps today's sequence.
- Result: `Touch MT ready` on 3 of 3 boots, with touch events flowing.
- The J714s line may differ; check your own ADT.
- Patches: `contrib/pending/trackpad/` (= integration 0001-0002). Report: `contrib/pending/trackpad/REPORT.md`. Log: [`logs/02-trackpad-afe-reset-P3-boot1.txt`](logs/02-trackpad-afe-reset-P3-boot1.txt).

### iBoot boot-failure counter

- With `POWER_RESET_MACSMC=m` and no modules on the root, Linux never wrote `boot_stage` /
  `boot_error_count` in the PMU scratchpad. Every watchdog restart from Linux counted as a failed
  boot. After a few, iBoot showed the "needs to be reinstalled" recovery, and only a macOS boot
  cleared it.
- Patch 0017 (on top of platform patch 0040) builds `macsmc-reboot` in as poweroff-only. Restart
  stays on the watchdog, but `boot_stage` is set to 0 before a restart. It uses the Abbey PMU
  scratchpad cells `boot_stage` 0xf801, counts 0xf802, `shutdown_flag` 0xf80f bit 3.
- Verified on hardware over four Linux boots. On the first reboot the driver logged `PMU logged 1
  boot error(s) and 0 panic(s)` and cleared it (0xf802 -> 0x00). The B2 payload (old DTB, sha256
  `55d95928...`) then went through three consecutive Linux (watchdog) reboots with zero PMU boot
  errors (the driver only prints when a count is non-zero), the scratchpad unchanged, NVMe up at
  8.9-11.6 s, `Touch MT ready` and 18 CPUs on every boot. Log:
  [`logs/04-macsmc-reboot-boot-counter.txt`](logs/04-macsmc-reboot-boot-counter.txt).
